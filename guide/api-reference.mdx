## Authentication

All non-public endpoints require an `x-api-key` header.

```http
x-api-key: your_api_key
```

API keys are scoped by role (`client`, `orchestrator`, `worker`, `validator`). Each role has access only to the routes relevant to that role.

Validator routes are the exception: they authenticate with a hotkey signature rather than a key, and a validator obtains its key from the heartbeat response. See [Validators](./validators.md) for the header format and the issuance flow.

## Supported APIs

Participant operations and transfer control use [BeamCore](https://beamcore.b1m.ai). Its [OpenAPI schema](https://beamcore.b1m.ai/openapi.json) describes the supported role-scoped contracts.

Delayed telemetry uses `https://api.b1m.ai`. Supply a customer organization key with `telemetry:read` permission in `x-api-key`. Reads use credits and the applicable API limits. Responses are private and must not be cached.

Find request fields, response examples and errors in the [supported API reference](https://docs.b1m.ai/api).

| Read | Route |
| --- | --- |
| Orchestrator profiles | `/v1/telemetry/participants/orchestrator` |
| Details and history | `/v1/telemetry/participants/orchestrator/{id}` and `/{id}/history` |
| Network and history | `/v1/telemetry/network` and `/network/history` |
| Transfers | `/v1/telemetry/transfers` and `/transfers/{id}` |
| Tasks and participant performance | `/v1/telemetry/tasks?transferId={id}` and `/v1/telemetry/transfers/{id}/participants` |
| Assignment and event evidence | `/v1/telemetry/transfers/{id}/assignments` and `/events` |
| Scoring and audit evidence | `/v1/telemetry/audit/{kind}/{id}` |
| Published emission epochs | `/v1/telemetry/epochs` |
| An epoch's orchestrator ranks and shares | `/v1/telemetry/epochs/{epoch}/orchestrators` |
| Scoped public transfer proof | `/v1/audit/transfers/{id}/assignment-plan` |
| Scoped public scoring proof | `/v1/audit/scoring/{epoch}/{kind}/{id}` |

Transfer IDs may be UUIDs or room publication IDs beginning with `btr_pub_`. Lists, histories, task, participant-performance and assignment reads support a `workload` filter. Detail reads return all profiles. Keep the same filters while following `nextCursor`; use the returned snapshot identity to pin a version where supported.

Epoch reads use the history price tier. Their pages belong to one complete published version; filtering by workload keeps the recorded global ranks and emission shares.

Telemetry releases after one subnet epoch, or after 60 minutes when the clock is unavailable. Snapshot metadata identifies the version, observation and publication times, and evidence cutoff. Corrections produce a new delayed version. Published telemetry snapshots are available for up to 30 days from their observation time. Public audit reads are narrowly scoped and rate limited.

See [PRISM scoring](./prism) for a friendly explanation of points and workload profiles.
